# Architecture Proposals for a Go OS-Signal Event Adapter

## Executive summary

This document proposes four architectures for a generic Go package that maps Unix OS signals to user-defined values:

1. a single-consumer event stream;
2. a callback dispatcher;
3. a context-oriented pull API; and
4. a fan-out subscription bus.

The **single-consumer event stream** is the recommended default. It has the smallest useful API, makes ownership clear, preserves ordering, composes naturally with `select`, and can stop without depending on arbitrary user code.

Use the **context-oriented pull API** for simpler request/response loops where exposing a channel would add no value. Use the **fan-out subscription bus** for highly concurrent pub/sub use cases requiring independent slow-consumer policies. Use the **callback dispatcher** only when callback ergonomics are essential and handlers can honor cancellation and bounded execution-time contracts.

## Assumptions

- The implementation targets Go 1.26 and Unix systems.
- The package is named `signalmap`. The name is short, does not stutter with the proposed exported identifiers, and describes the package's responsibility.
- User events have type parameter `E any`. Events do not need to be comparable, and the adapter does not inspect or copy event values.
- An adapter instance is in-process and owns one signal registration. Cross-process delivery and durable event storage are out of scope.
- The mapping is immutable after construction. A caller creates another instance to use another mapping.
- The package can guarantee behavior only for signals that reach its registration channel. Unix and `os/signal` may coalesce repeated signals, and `os/signal` uses non-blocking delivery to its registered channel. No architecture can guarantee one event for every signal generated by the OS.
- User code does not close package-owned channels.
- Callback code is cooperative: it returns in bounded time and observes its context. Go cannot forcibly terminate an arbitrary callback that blocks forever.
- The architectures are alternatives. Their API sketches are not intended to coexist unchanged in one package.

## Common design foundation

### Mapping and configuration

Each constructor accepts `map[os.Signal]E`. The constructor:

1. rejects a nil or empty mapping with `ErrEmptyMapping`;
2. rejects a nil signal key with `ErrInvalidSignal`;
3. rejects signals known to be uncatchable on Unix, notably `SIGKILL` and `SIGSTOP`;
4. copies every key and value into package-owned storage; and
5. derives a stable signal slice from the copy before registration.

A map makes duplicate signal keys impossible. Multiple signals may map to the same event because `E` is intentionally not constrained by `comparable`.

There is no portable standard-library query that proves an arbitrary `os.Signal` is supported and catchable on every Unix variant. The implementation should use build-specific validation for definitely invalid or uncatchable values but should not maintain a fragile universal allowlist. Platform-specific signal constants that do not exist fail at compile time on that platform. Remaining registration behavior must be covered by platform integration tests and documented.

Only mapped signals are registered. An unmapped signal received from a fake or faulty source is ignored. It is not treated as a zero-value event.

### Signal-source boundary

Internal code should not call package globals throughout the implementation. It should depend on a small, unexported source abstraction:

```go
type signalSource interface {
	Register(signals []os.Signal, buffer int) (signalRegistration, error)
}

type signalRegistration interface {
	Signals() <-chan os.Signal
	Stop()
}
```

The production source creates a buffered channel, calls `signal.Notify`, and returns a registration whose `Stop` method calls `signal.Stop` exactly once. The registration does not need to close the signal channel. After `signal.Stop` returns, `os/signal` will no longer send to it, and the channel becomes collectible after the worker releases it.

The source is unexported because test injection is an implementation concern, not part of the normal user API. Package tests use an unexported constructor that accepts a fake source. The fake records registrations and cleanup calls and can inject signals deterministically. External black-box tests exercise only the public API.

The production ingress buffer defaults to `max(1, len(mapping))`. A configuration option may increase it for bursty workloads. A larger buffer reduces—but cannot eliminate—upstream loss.

### Lifecycle

All variants use this one-way state machine:

```text
New -> Starting -> Running -> Stopping -> Stopped
          \---------------------------> Stopped
```

`New` is the only state from which a start may claim the instance. Before claiming it, `Start` validates its context and other call arguments. A call rejected by argument validation leaves the instance in `New`.

Once a valid `Start` call atomically changes `New` to `Starting`, the instance never returns to `New`. Registration failure changes it to `Stopped`; another start still returns `ErrAlreadyStarted`. This strict rule avoids hidden reset races and satisfies the lifetime-wide single-start requirement.

| Method/state | New | Starting | Running | Stopping | Stopped |
|---|---|---|---|---|---|
| `Start` | Claims the instance | `ErrAlreadyStarted` | `ErrAlreadyStarted` | `ErrAlreadyStarted` | `ErrAlreadyStarted` |
| `Stop` | `ErrNotStarted` | Requests stop and waits | Requests stop and waits | Joins existing stop | Returns `nil` |
| Receive/`Next` | Variant-specific not-started result | Wait or not-started result | Valid | May drain accepted buffered events | Drains retained events, then stopped result |
| Subscribe | Variant-specific | Serialized with startup | Variant-specific | `ErrStopped` | `ErrStopped` |

One mutex protects the lifecycle state, registration reference, cancellation function, and completion channel. Event data does not use that mutex. The first successful transition to `Stopping` closes or cancels a private stop signal. Exactly one coordinator or worker owns final cleanup and changes `Stopping` to `Stopped`.

If `Stop(ctx)` is used, it always initiates shutdown before waiting. If its context expires, it returns `ctx.Err()` while shutdown continues. Concurrent stop callers wait on the same completion channel. A stop racing with `Starting` records a stop request; startup either cleans up a completed registration immediately or records the registration for the coordinator to clean up. It cannot publish a live worker after stop completion.

Cancellation of the context passed to `Start` is equivalent to requesting `Stop`, except that no public caller is waiting for completion. Shutdown remains observable through channel closure, `Next`, or a subsequent idempotent `Stop`.

### Common errors

The package should use a small sentinel set:

```go
var (
	ErrAlreadyStarted = errors.New("signalmap: already started")
	ErrNotStarted     = errors.New("signalmap: not started")
	ErrStopped        = errors.New("signalmap: stopped")
	ErrEmptyMapping   = errors.New("signalmap: empty mapping")
	ErrInvalidSignal  = errors.New("signalmap: invalid signal")
	ErrInvalidBuffer  = errors.New("signalmap: invalid buffer size")
	ErrNilHandler     = errors.New("signalmap: nil handler")
)
```

Operational errors are wrapped with context and `%w`, for example `fmt.Errorf("register signals: %w", err)`. Context cancellation is returned as `context.Canceled` or `context.DeadlineExceeded`. There is no error hierarchy or reflection-based classification.

A nil `context.Context` is a programmer error in idiomatic Go. Public methods should document that contexts must be non-nil and may panic consistently with standard context-accepting APIs, rather than adding a package-specific nil-context error.

### Ordering and signal multiplicity

For signals accepted by the source channel, the coordinator processes values in receive order. Each received mapped signal creates one mapped event. If the source receives the same signal three times, the adapter creates three events.

This ordering statement does not imply that the OS or `os/signal` retains every occurrence. Standard signal semantics may merge identical pending signals, and a full registration channel can lose notifications before the adapter sees them.

## Variant 1: Single-consumer event stream

### Description and intended use

This variant returns a receive-only channel from `Start`. It is appropriate when one caller owns signal handling or intentionally distributes work by allowing multiple goroutines to compete on the same channel.

It is the closest fit to normal Go control-flow: the caller selects over mapped events, other application channels, and context cancellation without registering callbacks or managing subscriptions.

### Public API sketch

```go
package signalmap

type StreamOption interface {
	applyStream(*streamConfig) error
}

func WithEventBuffer(size int) StreamOption
func WithSignalBuffer(size int) StreamOption

type Stream[E any] struct {
	// unexported
}

func NewStream[E any](
	mapping map[os.Signal]E,
	opts ...StreamOption,
) (*Stream[E], error)

func (s *Stream[E]) Start(ctx context.Context) (<-chan E, error)
func (s *Stream[E]) Stop(ctx context.Context) error
```

The default event buffer is zero: the event channel is unbuffered and naturally applies backpressure. `WithEventBuffer` permits a bounded non-negative capacity. The signal ingress buffer must be positive. Options are used here because the two independent capacities are optional tuning controls; they should remain few and validated.

### Core components and concurrency model

- An immutable copied mapping.
- The lifecycle mutex and completion channel described above.
- One source registration.
- One event channel, created during construction but returned only after successful startup.
- One worker goroutine that owns all event-channel sends and is the only goroutine allowed to close it.
- One derived run context canceled by either the parent context or `Stop`.

After registration succeeds, `Start` safely publishes the registration and worker under the lifecycle lock, changes state to `Running`, and returns the receive-only event channel. The worker loops on the registration channel and cancellation.

For every mapped signal, it uses a cancellation-aware blocking send:

```go
select {
case events <- mapped:
	// Accepted by the output channel.
case <-runCtx.Done():
	return
}
```

The worker's deferred cleanup calls `registration.Stop`, closes the event channel, and publishes `Stopped`. The event channel is never closed by `Stop` or by a receiver.

### Lifecycle and cancellation

`Start` is asynchronous: success means registration and the worker are active, not that an event has arrived. A second start always returns `ErrAlreadyStarted`.

`Stop` cancels the run context and waits for the worker. Cancellation releases an event send blocked by a slow consumer. Cleanup unregisters signal delivery before reporting completion.

At shutdown:

- events already placed in the output buffer remain readable after the channel is closed;
- the current event is discarded if it was waiting on a blocked send and cancellation wins;
- signals still buffered at the source are discarded; and
- no new event is accepted after the worker observes cancellation.

An event send and cancellation that become ready simultaneously may be selected in either order, as permitted by Go `select`. Therefore, one already-mapped event may be delivered while stop races with the send.

### Delivery, backpressure, and ordering

This is a work-queue channel, not fan-out. With one receiver, that receiver gets all events accepted by the event channel. With multiple receivers, each event goes to exactly one receiver, selected by channel scheduling.

Delivery from the worker is blocking and lossless while running, subject to cancellation. A slow receiver backpressures the worker. If the source ingress channel then fills, `os/signal` may drop later notifications. The package does not silently add another unbounded queue.

Events preserve source receive order at the output send boundary. Multiple competing receivers may complete their application work out of order.

### Validation and error model

Construction applies common mapping validation. Negative event capacity or non-positive signal capacity returns `ErrInvalidBuffer`. Invalid options fail construction.

`Start` returns registration errors. After such an error, the instance is stopped and cannot be restarted. `Stop` follows the shared lifecycle error rules.

### Testing strategy

- Inject signals through a fake source and compare exact mapped output order.
- Verify that the constructor copied the mapping by mutating the caller's map after construction.
- Verify an unbuffered send blocks until a receiver exists.
- Fill a buffered output, stop the stream, and verify the blocked worker terminates and the accepted buffer remains drainable.
- Race many `Start` calls and assert exactly one succeeds.
- Race parent cancellation and `Stop`; assert one cleanup call, one channel close, and no stuck goroutine.
- Return a fake registration error and verify all later starts return `ErrAlreadyStarted`.
- Run all concurrent tests under `go test -race`.
- In Unix-only integration tests, send a catchable signal to the test process, receive its mapping, stop, and verify normal signal behavior is restored. Isolate these tests because process signals can interfere with parallel test execution.

### Pros

- Small, idiomatic API that works directly with `select` and `range`.
- Clear channel ownership and a single channel-closing goroutine.
- Strong ordering for accepted events.
- Blocking sends are cancellation-safe and require no per-consumer goroutines.
- Easy deterministic testing.

### Cons

- No broadcast semantics.
- A slow receiver can indirectly increase upstream signal loss.
- Multiple channel receivers compete rather than each receiving a copy.
- Backpressure policy is fixed to blocking.

### Risks

- Users may incorrectly assume every physical OS-signal occurrence is delivered.
- Users may accidentally start multiple competing consumers expecting fan-out.
- An excessively small source buffer may lose bursty signals.

### Usage limitations

- Best for one logical consumer.
- Not suitable when every subscriber must observe every event.
- Not suitable when slow consumers must be isolated from each other.
- Buffered values retain their event objects until consumed or until the stream becomes unreachable.

## Variant 2: Callback dispatcher

### Description and intended use

This variant invokes registered context-aware handlers when mapped events arrive. Each subscription has a bounded mailbox and one worker, so a slow handler can be isolated from other handlers when a dropping overflow policy is used.

It is useful in frameworks that already organize lifecycle behavior as callbacks. It is less suitable for infrastructure libraries because arbitrary user functions create shutdown and panic concerns that channel APIs avoid.

### Public API sketch

```go
type OverflowPolicy uint8

const (
	DropNewest OverflowPolicy = iota
	DropOldest
	Block
)

type Handler[E any] func(context.Context, E) error

type HandlerError[E any] struct {
	SubscriptionID uint64
	Event          E
	Err            error
}

func (e *HandlerError[E]) Error() string
func (e *HandlerError[E]) Unwrap() error

type Subscription interface {
	ID() uint64
	Unsubscribe() error
	Wait(context.Context) error
	Dropped() uint64
}

type Dispatcher[E any] struct {
	// unexported
}

func NewDispatcher[E any](
	mapping map[os.Signal]E,
	handlerBuffer int,
	policy OverflowPolicy,
) (*Dispatcher[E], error)

func (d *Dispatcher[E]) Subscribe(handler Handler[E]) (Subscription, error)
func (d *Dispatcher[E]) Errors() <-chan error
func (d *Dispatcher[E]) DroppedErrors() uint64
func (d *Dispatcher[E]) Start(ctx context.Context) error
func (d *Dispatcher[E]) Stop(ctx context.Context) error
```

`Errors` returns one package-owned, bounded error channel. The dispatcher closes it only after its coordinator and all cooperative handler workers have exited. The error channel carries handler failures wrapped as `HandlerError[E]`. If the error channel is full, the dispatcher drops the newest error report and increments the counter returned by `DroppedErrors`.

### Core components and concurrency model

- A coordinator goroutine owns the active subscription registry and all mailbox offers.
- Each subscription has a stable numeric ID, bounded mailbox, cancellation context, completion channel, atomic drop count, and one handler worker.
- Subscribe, unsubscribe, stop, and source events reach the coordinator as commands.
- Subscription definitions added in `New` are protected by the lifecycle mutex. At startup, ownership transfers to the coordinator.
- A worker invokes its handler sequentially, so one subscription never has concurrent calls and observes events in mailbox order.

`Subscribe` is valid in `New` and `Running`. A call racing with startup is linearized under the lifecycle mutex: it is either part of the startup snapshot or sent as a coordinator command after `Running` is published. It is rejected with `ErrStopped` in `Stopping` or `Stopped`.

`Unsubscribe` is idempotent. Its coordinator acknowledgement means no future event will be added to that mailbox. It cancels the handler context and discards mailbox entries not already passed to the handler. It does not wait for an in-flight handler, which allows a handler to unsubscribe itself without deadlocking. `Wait` is the explicit operation for awaiting handler-worker exit.

### Lifecycle and cancellation

`Start` registers signals, starts the coordinator and subscription workers, and returns after publishing `Running`. A parent-context cancellation or `Stop`:

1. stops accepting source events;
2. unregisters the source;
3. cancels every subscription context;
4. prevents further mailbox offers;
5. discards events still waiting in mailboxes;
6. waits for handler workers; and
7. closes the error channel and publishes `Stopped`.

`Stop(ctx)` can return `ctx.Err()` if a handler has not finished by the deadline. Source cleanup and dispatcher shutdown still continue. If a handler never returns, its worker cannot complete and full stopped completion cannot be reported.

That limitation is fundamental: Go provides no safe way to kill a goroutine executing arbitrary user code. The API contract must require handlers to return promptly after their context is canceled. A service that cannot enforce that contract should use the stream or bus variant instead.

### Delivery, backpressure, and ordering

Every source event is offered to every subscription active at the coordinator's event linearization point.

- `DropNewest`: if a subscription mailbox is full, discard the incoming event and increment that subscription's drop count. This is the recommended default.
- `DropOldest`: evict the oldest queued event, enqueue the incoming event, and increment the drop count. The mailbox should be a coordinator-managed bounded ring rather than a channel receive trick, so eviction is deterministic.
- `Block`: wait for space or dispatcher cancellation. This preserves accepted events but one slow handler backpressures all subscriptions and can increase upstream signal loss.

Per-subscription order is preserved among retained events. Different handlers execute concurrently, so there is no cross-handler completion order. Duplicate source deliveries produce duplicate callback invocations unless overflow drops one.

Registration is linearizable: a subscription receives events processed after its successful subscribe acknowledgement. Unsubscription is also linearizable: no event processed after its acknowledgement is offered to that subscription.

### Handler errors and panics

A returned handler error is an application delivery error, not a dispatcher failure. It is reported on `Errors`; the subscription remains active.

The package should recover a panic at the handler-call boundary, convert it to a `HandlerError` that includes a stack trace, and then terminate that subscription. Recovery here is justified because the handler runs in a package-owned worker and an unhandled panic would terminate the process. The package must not silently continue invoking a handler whose invariants may be broken.

Panic recovery does not help a handler that blocks forever.

### Validation and errors

The constructor validates the common mapping, non-negative handler buffer, and known overflow policy. `Subscribe(nil)` returns `ErrNilHandler`. Subscribe after shutdown returns `ErrStopped`. Unsubscribe is idempotent and returns `nil` after its first successful removal.

Registration and lifecycle errors use the common model. Delivery drops are observable counters, not synchronous errors, because the signal producer has no caller to return them to.

### Testing strategy

- Verify each handler gets the same mapped event and each subscription preserves order.
- Add and remove subscriptions concurrently with signal injection and assert acknowledgement-boundary semantics.
- Block one handler and verify `DropNewest` does not block another handler.
- Exercise `DropOldest` with a deterministic ring and verify the exact retained sequence.
- Exercise `Block`, then cancel and verify the coordinator exits its blocked offer.
- Return handler errors and verify wrapping, event association, and error-channel closure.
- Panic in a handler and verify recovery, stack capture, and termination of only that subscription.
- Self-unsubscribe from a handler and verify no deadlock.
- Use a deliberately non-cooperative handler to verify `Stop` respects its caller deadline and document that the handler worker remains the user's unresolved fault.
- Race startup, subscription, unsubscription, and stopping under `go test -race`.

### Pros

- Natural integration with callback-oriented applications.
- Broadcast delivery with per-handler ordering.
- Bounded mailboxes isolate slow handlers under dropping policies.
- Subscription acknowledgement gives precise concurrent add/remove semantics.
- Handler errors have an explicit asynchronous path.

### Cons

- Significantly more machinery than a channel stream.
- Requires one worker per active subscription.
- Shutdown depends on cooperative user code.
- Error-channel backpressure needs its own documented loss behavior.
- Panic handling and self-unsubscription add complexity.

### Risks

- A handler that ignores cancellation can permanently retain its worker and captured objects.
- `Block` policy allows one handler to affect all others.
- Drop policies can hide important lifecycle events unless counters are monitored.
- Recovering handler panics may conflict with an application's process-wide panic policy.

### Usage limitations

- Handlers must be concurrency-safe with the rest of the application and must return promptly.
- This architecture cannot provide an unconditional no-goroutine-leak guarantee against malicious or defective handler code.
- It is not appropriate when every mapped event must be durably retained.
- It should not be the package default.

## Variant 3: Context-oriented pull API

### Description and intended use

This variant hides channels behind a blocking `Next(ctx)` operation. It is intended for a simple sequential loop that needs per-wait deadlines or cancellation but does not need to compose the event stream directly in a `select`.

Multiple goroutines may call `Next` safely. They compete for events: each queued event is returned to one caller.

### Public API sketch

```go
type Waiter[E any] struct {
	// unexported
}

func NewWaiter[E any](
	mapping map[os.Signal]E,
	capacity int,
) (*Waiter[E], error)

func (w *Waiter[E]) Start(ctx context.Context) error
func (w *Waiter[E]) Next(ctx context.Context) (E, error)
func (w *Waiter[E]) Stop(ctx context.Context) error
func (w *Waiter[E]) Dropped() uint64
```

`capacity` must be positive. It bounds the internal event queue. A positive capacity avoids requiring an active `Next` caller at the instant a signal arrives.

### Core components and concurrency model

- One worker receives source signals and maps them.
- One bounded internal event channel is written and closed only by that worker.
- Any number of callers receive from the event channel through `Next`.
- An atomic counter records events dropped because the queue was full.
- Lifecycle state and source cleanup follow the common foundation.

For each mapped signal, the worker performs a non-blocking queue offer:

```go
select {
case events <- mapped:
default:
	dropped.Add(1)
}
```

The policy is deliberately fixed to drop-newest. Adding several overflow options would undermine the main value of this variant: a compact, predictable API.

`Next` first rejects calls made before successful startup with `ErrNotStarted`. While running or draining, it waits for an event or its own context:

```go
select {
case event, ok := <-events:
	if !ok {
		return zero, ErrStopped
	}
	return event, nil
case <-ctx.Done():
	return zero, ctx.Err()
}
```

If both an event and context cancellation are ready, either result may win according to Go `select` semantics. A returned event has been consumed and will not be offered to another waiter.

### Lifecycle, shutdown, and queue ownership

`Start` does not expose the internal event channel. Parent cancellation and `Stop` stop source delivery and make the worker close the queue.

Values already queued when stopping begins remain available to `Next`. Once the queue is drained, `Next` returns `ErrStopped`. Events still in the source channel are discarded. This retained-drain policy prevents silently losing values the adapter already counted as accepted.

The worker is the only queue sender and closer, so concurrent `Next` and `Stop` cannot produce a send-on-closed-channel panic.

### Context orientation and `signal.NotifyContext`

`signal.NotifyContext` is attractive for one-shot shutdown notification, but it cancels a context without reporting which registered signal caused cancellation. A canceled context also stays canceled, so it cannot represent repeated signals such as multiple reload requests.

This architecture therefore uses ordinary source registration to retain signal identity and uses contexts for:

- adapter lifetime through `Start`;
- individual wait cancellation and deadlines through `Next`; and
- bounded shutdown waits through `Stop`.

A separate `NotifyContext`-only architecture would be valid only for one-shot, identity-free shutdown. It would not satisfy the general remapping and repeated-event requirements.

### Delivery, backpressure, and ordering

This is single-consumer-per-event delivery. Concurrent waiters receive distinct events, with the winning waiter chosen by channel scheduling.

Queued events retain source receive order. Concurrent callers may finish processing them out of order. When full, the newest event is dropped and `Dropped` increases. The counter does not include notifications lost before the source channel receives them.

### Validation and errors

Construction validates the common mapping and requires capacity greater than zero. `Next` before start returns `ErrNotStarted`; after all retained events are drained it returns `ErrStopped`. Its own context error takes precedence only when the context branch wins.

Registration and stop errors use the common lifecycle model.

### Testing strategy

- Verify sequential `Next` results and exact mapping.
- Start multiple waiters and prove each injected event is returned exactly once.
- Fill the queue, inject another event, and verify drop-newest and the counter.
- Cancel an individual `Next` without stopping the adapter.
- Cancel the start context and verify queued values drain before `ErrStopped`.
- Race `Next`, `Stop`, and source injection under `go test -race`.
- Verify only the worker closes the internal queue and source cleanup occurs once.

### Pros

- Very small call-oriented API.
- Per-call deadlines and cancellation are explicit.
- No channel ownership exposed to callers.
- Bounded memory and observable local drops.
- Straightforward sequential application code.

### Cons

- Cannot be used directly as a `select` case.
- Fixed drop-newest behavior can lose events under load.
- Concurrent waiters compete; there is no broadcast.
- `Dropped` is cumulative and cannot identify which event was lost.

### Risks

- Callers may ignore the drop counter and assume lossless delivery.
- Callers may expect context cancellation to have deterministic precedence over a ready event.
- A capacity chosen too small increases loss; an excessive capacity retains event objects longer.

### Usage limitations

- Best for simple sequential consumers and bounded event rates.
- Not suitable for fan-out.
- Not suitable when blocking backpressure is required.
- Not a replacement for `signal.NotifyContext` when only one identity-free shutdown signal is needed; the standard library is simpler in that narrow case.

## Variant 4: Fan-out subscription bus

### Description and intended use

This variant broadcasts every accepted mapped event to every subscription active at that event's linearization point. Each subscriber gets a receive-only channel and an independent bounded mailbox with its own overflow policy.

It is intended for long-lived services where several independent components react to shutdown, reload, diagnostic, or application-specific signal events.

### Public API sketch

```go
type SubscribeConfig struct {
	Buffer   int
	Overflow OverflowPolicy
}

type EventSubscription[E any] interface {
	Events() <-chan E
	Unsubscribe() error
	Dropped() uint64
}

type Bus[E any] struct {
	// unexported
}

func NewBus[E any](mapping map[os.Signal]E) (*Bus[E], error)
func (b *Bus[E]) Subscribe(cfg SubscribeConfig) (EventSubscription[E], error)
func (b *Bus[E]) Start(ctx context.Context) error
func (b *Bus[E]) Stop(ctx context.Context) error
```

The default recommendation is a small positive buffer with `DropNewest`; callers must supply the concrete `SubscribeConfig` so backpressure is a visible decision. `Block` is supported but should be used only when global backpressure is acceptable.

### Core components and shared-state ownership

- One coordinator goroutine owns the live subscriber registry and linearizes source events, subscribe commands, unsubscribe commands, and stop.
- Each subscriber has a bounded mailbox, a receive-only public event channel, an atomic drop count, and one pump goroutine.
- The coordinator is the only mailbox producer.
- The pump is the only public event-channel sender and closer.
- A mailbox uses a bounded ring plus space/data notifications. This makes `DropOldest` exact and lets the pump block on a subscriber send without blocking non-blocking offers to other subscribers.

Before startup, subscriptions are stored under the lifecycle mutex. At startup, the coordinator receives ownership of that snapshot. A subscribe racing with startup is included in the snapshot or acknowledged by the running coordinator; it is never missed between the two.

The coordinator command acknowledgement is the operation's linearization point:

- after `Subscribe` returns, all subsequently processed events are offered to it;
- after `Unsubscribe` returns, no subsequently processed event is offered to it.

The caller must not close `Events`. `Unsubscribe` is idempotent.

### Lifecycle and cancellation

`Subscribe` is valid in `New` and `Running`, and returns `ErrStopped` during or after shutdown.

On parent cancellation or `Stop`, the coordinator:

1. stops accepting source events and calls `registration.Stop`;
2. removes all mailboxes from the registry;
3. signals every pump to stop;
4. discards mailbox values not yet transferred to public event buffers;
5. waits for pumps to exit; and
6. publishes `Stopped`.

Each pump exits a blocked public-channel send through a stop-aware `select`, then closes its public event channel. Values already in the public channel buffer remain readable after close. Values still in its private mailbox are discarded. This boundary is chosen because draining private queues could make shutdown arbitrarily slow.

Unsubscription applies the same per-subscriber rule: discard the private mailbox, interrupt any blocked send, close the public channel, and retain only values already buffered in that public channel.

### Delivery, backpressure, and ordering

Every active subscriber is offered every source event. Delivery is best-effort under dropping policies and blocking while running under `Block`.

- `DropNewest`: keep queued events and reject the incoming event for only that subscriber.
- `DropOldest`: remove that subscriber's oldest private queued event and retain the incoming event.
- `Block`: wait for that subscriber's private mailbox to have space, or for shutdown. Because the coordinator is blocked, this delays all subscribers and can lead to upstream signal loss.

Each subscriber preserves order among the events retained by its policy. Subscribers can observe different subsets and complete at different times. Duplicate accepted source signals generate duplicate offers.

Drop counters are per subscription and count only mailbox policy drops. They cannot count upstream loss by the OS or source channel.

### Validation and errors

Construction applies common mapping validation. Subscribe rejects negative buffers and unknown policies. An unbuffered public channel is allowed, but a zero private capacity is incompatible with drop-oldest semantics and should be rejected for that policy.

Subscribe during shutdown returns `ErrStopped`. Unsubscribe is idempotent. Start and stop use the common lifecycle and registration errors.

There is no synchronous per-delivery error because signal receipt has no requesting caller. Drop counters are the explicit delivery-failure signal.

### Testing strategy

- Verify every active subscriber gets every event under adequate capacity.
- Verify exact retained sequences for drop-newest and drop-oldest.
- Block one subscriber and prove dropping policies do not delay another subscriber.
- Verify `Block` backpressures the coordinator and cancellation releases it.
- Subscribe and unsubscribe concurrently with injection and assert acknowledgement-boundary semantics.
- Stop with pumps blocked on unbuffered public channels and verify all pumps exit and channels close exactly once.
- Verify buffered public values remain readable while private mailbox values are discarded.
- Race subscription churn, source input, and stop under `go test -race`.
- Repeatedly construct, start, stop, and release buses in a leak test with a fake source; use goroutine profiles only as supporting evidence rather than brittle exact counts.

### Pros

- Correct broadcast semantics.
- Independent buffers and drop accounting isolate slow subscribers.
- Precise concurrent subscription boundaries.
- Receive-only channels retain idiomatic `select` and `range` use.
- Supports both freshness-oriented and retention-oriented bounded policies.

### Cons

- Highest implementation complexity.
- One pump goroutine and mailbox per subscriber.
- `Block` undermines slow-subscriber isolation.
- More configuration and operational monitoring are required.
- Shutdown has two buffering layers with a deliberately explicit discard boundary.

### Risks

- High subscription churn can create avoidable goroutine and allocation overhead.
- Unread public buffers retain event values after unsubscribe until the subscription becomes unreachable.
- Misusing `Block` can cause global stalls.
- Drop counters can diverge across subscribers and require monitoring.

### Usage limitations

- Not justified for a single logical consumer.
- Does not provide durable or replayable events.
- Subscriber count and buffer sizes must be bounded operationally.
- Delivery completion across subscribers is intentionally unordered.

## Comparison

| Variant | Delivery model | Slow-consumer behavior | Ordering | Goroutines | Complexity | Best use |
|---|---|---|---|---:|---|---|
| Single-consumer stream | One event to one channel receiver | Blocking; can increase upstream loss | Source order at channel sends | 1 | Low | Recommended general default |
| Callback dispatcher | Broadcast to handlers | Per-handler drop/block policy | Per-handler retained order | 1 + handlers | High | Callback-oriented frameworks |
| Context pull | One event to one `Next` caller | Drop newest when queue is full | Queue order | 1 | Low | Simple sequential loops |
| Fan-out bus | Broadcast to subscriber channels | Per-subscriber drop/block policy | Per-subscriber retained order | 1 + subscribers | Highest | Highly concurrent pub/sub |

## Recommendation

### Default: single-consumer event stream

The stream is the best default because it has one clear owner, one worker, one closing site, and normal Go channel semantics. It supports cancellation without depending on user callbacks and exposes enough control for most services without building a subscription framework into a signal adapter.

Choose a bounded event buffer when the main loop can be temporarily busy. Keep the blocking policy: it is explicit, testable, and avoids silently inventing package-level loss. Document that source-level loss remains possible.

Do not use the stream when several independent components must each see the same event or when one slow component must be isolated from others.

### Simpler cases: context-oriented pull

The pull API is best when application code naturally says “wait for the next mapped signal with this deadline” and does not need channel composition. It has a smaller usage surface than subscriptions and makes individual wait cancellation explicit.

For an identity-free, one-shot shutdown signal, neither custom pull nor remapping is necessary: use `signal.NotifyContext` directly.

### Highly concurrent pub/sub: fan-out bus

The bus is the best fit when many independently paced subscribers must observe the same events. Its coordinator establishes deterministic add/remove boundaries, and per-subscriber mailboxes isolate slow readers under dropping policies.

The added goroutines, queues, and shutdown rules are real costs. They should be accepted only when broadcast and isolation are actual requirements.

### Callback use

Callbacks are an integration choice, not the default architecture. They are reasonable when the surrounding framework already manages handlers and can enforce prompt, context-aware completion. A package that promises unconditional goroutine cleanup cannot make that promise for arbitrary callback code.

## Style-guide alignment

- Constructors validate required invariants and return useful errors.
- Exported names avoid package-name stutter: `signalmap.NewStream`, not `signalmap.NewSignalMapStream`.
- Interfaces are small and introduced only at ownership boundaries.
- `context.Context` is the first method parameter and is never stored beyond the operation except the lifetime context explicitly passed to `Start`.
- Returned channels are receive-only, and ownership and closure are documented.
- Mutable state has one named owner: lifecycle fields use one mutex; event flow is coordinator- or worker-owned; counters use atomics.
- No user callback or channel operation occurs while holding the lifecycle mutex.
- No global mutable state, reflection, or `unsafe` is required.
- Sentinel errors support `errors.Is`; contextual failures use `%w`.
- Exported identifiers require comments describing contracts, especially start-once behavior, shutdown draining, loss, and channel ownership.
- Configuration remains concrete and bounded. Options are used only where they materially improve the stream constructor.

## Cross-variant acceptance tests

An implementation of any chosen variant should satisfy these acceptance criteria:

1. A caller-provided mapping cannot be mutated to change live behavior.
2. Exactly one valid concurrent start claims an instance; every later start returns `ErrAlreadyStarted`.
3. A claimed instance never returns to `New`, including after registration failure.
4. Concurrent stop calls cause exactly one signal unregistration and all observe the same completion.
5. Stop can release every package-controlled blocked send or receive.
6. Source cleanup completes before stopped completion is published.
7. Every package-owned channel has exactly one closing owner, and callers receive only receive-only views.
8. Accepted events follow each variant's stated ordering, broadcast, overflow, and shutdown-retention rules.
9. Fake-source tests are deterministic and do not require process signals.
10. Unix integration tests restore signal handling and do not run in parallel with other process-signal tests.
11. `go test -race ./...` reports no races.
12. Leak-focused tests show no package-owned goroutines remain after cooperative consumers or handlers stop.

## Final checklist

- Concurrency safety: covered through explicit mutex, coordinator, worker, channel, and atomic ownership.
- Lifecycle: covered with a one-way state machine and per-method state behavior.
- Cancellation: covered for parent contexts, explicit stop, blocked sends, and per-call waits.
- Signal cleanup: `signal.Stop` is called exactly once before shutdown completion.
- Mapping validation: nil/empty maps, nil and uncatchable signals, duplication, platform limits, map copying, shared event values, and unmapped inputs are covered.
- Delivery semantics: one-consumer versus fan-out, duplicates, loss, ordering, and shutdown buffering are explicit.
- Backpressure: blocking, bounded buffering, drop-newest, drop-oldest, and slow-consumer isolation are compared.
- Testing: fake sources, lifecycle races, cancellation, slow consumers, subscriptions, race detection, leaks, and Unix integration are covered.
- Errors: a small sentinel set, wrapped operational errors, context errors, and asynchronous delivery failures are defined.
- Platform notes: Unix catchability and the limits of portable validation are stated.
- Style alignment: naming, interfaces, contexts, channel ownership, errors, and synchronization follow idiomatic Go, Effective Go, Google Go Style, and Uber Go Style principles.
